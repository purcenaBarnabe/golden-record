# Security and reputation audit — 2026-11-18

**Result:** No malicious behavior was found in the reviewed source or sampled live deployment. LinkedIn's stronger warning is reproducible for this application. Public checks did not identify a current listing for its hostname. A false positive or broader hosting-reputation rule is plausible; LinkedIn's actual rule/provider and any connection to post visibility remain unconfirmed.

Scope: checkout `c2d2eb0afab53f3c5bbc7f8326bda651a1eb9cda`, source/build/configuration review, dependency advisories, and public HTTP/DNS checks on November 18, 2026. No deployment, push, account changes, or appeal submission was performed.

## Verified findings

- LinkedIn's [link-safety page for the application](https://www.linkedin.com/safety/go?url=https%3A%2F%2Fvoyager-golden-record.pages.dev%2F) displays “Possible malicious content.” The same check for `https://pages.dev/` produces that warning. Controls for [NASA](https://www.linkedin.com/safety/go?url=https%3A%2F%2Fscience.nasa.gov%2F) and `https://developers.cloudflare.com/` display the ordinary “You’re leaving LinkedIn” notice. This is URL-dependent treatment, beyond the generic external-link notice described in [LinkedIn Help](https://www.linkedin.com/help/linkedin/answer/a1341680).
- The application serves HTTPS 200 without an outbound redirect. HTTP redirects once to the same hostname over HTTPS. Normal, LinkedInBot with LinkedIn referrer, and Googlebot requests returned identical HTML: 12,442 bytes; SHA-256 `da27443f011a3965ffc8e57d3ece2969b144709d437c435532031534e669bb02`. No cloaking was observed in these probes.
- A fresh production build reproduced all five deployed JavaScript bundles. The runtime bundle and both CSS files are byte-identical. The other four bundles match exactly after removing only the Sentry debug-ID prefix/suffix generated by `scripts/upload-sourcemaps.mjs`. HTML matches after excluding prerender timestamps and the hosting-added Cloudflare Analytics block. No unexplained injected application code was found.
- No credential/payment capture, automatic external navigation, open redirect, arbitrary evaluation, remote executable CDN loader, or service worker was found in authored source. All four public SVGs lack active scripts, event attributes, and external references. JSON-LD escapes `<`. Geometry compression/WASM and WebGL are legitimate rendering operations.
- Fonts, JavaScript, CSS, textures, geometry, and images are served locally. Runtime external integrations are Sentry ingestion, Cloudflare Analytics, and Internet Archive audio selected by the user. A sample audio HEAD request redirected within `archive.org` to `dn711109.ca.archive.org` and returned 200 `audio/mpeg`. NASA, Library of Congress, Wikimedia, Ozma, GitHub, and Archive references also appear as ordinary outbound links. `schema.org` and SVG namespace identifiers are not script downloads.
- The live CSP restricts resource origins and disables objects, framing, and form submission. `nosniff`, `DENY`, no-referrer, and restricted browser permissions are present. Inline bootstrap/style and WASM allowances support the existing framework/renderer; removing them without a demonstrated vulnerability is unwarranted.
- Requests for `.env`, `.git/config`, `package.json`, `_worker.js`, a nonexistent route, and a source-map filename returned the same homepage HTML through Pages' SPA fallback. Their status 200 does **not** indicate exposed secrets, source maps, or a deployed Worker.
- Yarn is pinned with a lockfile; dependencies resolve through registry packages. Reviewed lifecycle installers perform expected binary/native setup. Limited tracked-file secret-pattern checks found no matching credentials. The public Sentry DSN is an ingestion identifier. These checks do not certify every dependency or historical commit.
- GitHub Actions use pinned action SHAs, immutable installation and checks, separate static-artifact deployment, and isolated deployment credentials. Only `dist/client` is published. Development uses Vite/HMR; production uses a prerendered static export. Production also adds Cloudflare Analytics, Sentry release/debug IDs, and a lower default trace sampling rate. Source maps are removed after successful authenticated upload.

## Post restriction and possible explanations

The supplied [share URL](https://lnkd.in/p/d8tz4NQp) redirects to the [post](https://www.linkedin.com/posts/gustavopurcena_voyager1-goldenrecord-threejs-ugcPost-7528693959737630721-tVr4/) with an additional highlighted activity ID. The supplied screenshot explicitly says access to the **post** is restricted. A guest HEAD request returned 404; an ordinary GET instead redirected to LinkedIn signup. These guest responses cannot establish moderation or the audience actually applied to another signed-in member.

The following remain hypotheses:

- **Broader Pages reputation treatment:** the parent `pages.dev` receives the same stronger warning. Independent [SpiderLabs research](https://www.levelblue.com/blogs/spiderlabs-blog/its-raining-phish-and-scams-how-cloudflare-pages-dev-and-workers-dev-domains-get-abused) documents phishing hosted on other Pages tenants. This makes a hosting-related false positive plausible, but does not prove a blanket rule or implicate this application.
- **LinkedIn-specific or stale classification:** public checks and LinkedIn disagree. LinkedIn could use additional signals, different feeds, or a cached result; the responsible signal is unknown.
- **Separate post/account visibility or moderation issue:** owner visibility and recipient denial do not establish that the URL warning caused the restriction. For guests, [LinkedIn documents public-profile visibility as an additional requirement](https://www.linkedin.com/help/linkedin/answer/a523372/sharing-public-posts-on-and-off-linkedin?lang=en). That alone would not explain denial to other signed-in members.

No evidence justifies removing audio, Sentry, analytics, the 3D renderer, or legitimate external links. No domain changes or redirect workarounds were made.
